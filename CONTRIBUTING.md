# Contributing to Dream Team

The repo is the source of truth. **Never edit `~/.claude/` directly** — edit the repo and run `bun scripts/install.ts` (or `dreamteam install`) to sync. Everything below is small and copy-paste-able.

Setup:

```bash
git clone https://github.com/bondarewicz/dreamteam && cd dreamteam
bun install
bun test            # the gate: harness + web unit suites, LLM-free
```

The moat is the **eval harness** — every behaviour is graded, not vibed. The two highest-value contributions are **eval scenarios** and **agents**, both below.

---

## Add an eval scenario

Scenarios live in `evals/<agent>/scenario-*.md`. Each is one markdown file with YAML frontmatter + sections. Copy an existing one (e.g. `evals/bird/scenario-01-*.md`) and edit:

```markdown
---
id: <agent>-scenario-NN-short-slug
agent: <agent>            # bird | mj | shaq | kobe | pippen | magic | drexler
type: capability          # capability | edge_case | escalation | adversarial
prompt: |
  The exact task sent to the agent.
expected_behavior: |
  What a correct response does (the judge grades against this).
failure_modes: |
  Concrete ways to get it wrong (the judge penalizes these).
scoring_rubric: |
  pass / partial / fail criteria.
---

## Overview
One paragraph on what this scenario tests and why it matters.
```

Then:

```bash
dreamteam eval --agent <agent> --scenario <agent>/<id>            # run it (Claude/Max)
dreamteam eval --agent <agent> --scenario <agent>/<id> --provider ollama   # or any provider
dreamteam web                                                     # review scores at :3000
```

- The judge (Coach K) **always runs on Claude** so scores are comparable; `--model`/`--provider` only swaps the agent under test.
- Run `--trials 3` before claiming a score — a single trial can be lucky.
- Don't hand-write scores anywhere. Every score is a live run; the harness records it.

**Checklist:** ☐ frontmatter complete ☐ `expected_behavior` + `failure_modes` + `scoring_rubric` are concrete ☐ ran `--trials 3` ☐ scores reviewed in `dreamteam web`.

## Add or change an agent

Agents are one markdown file each: `agents/<name>.md` — YAML frontmatter (config) + body (system prompt).

```yaml
---
name: <name>
description: '<one line — when to use this agent>'
model:
  tier: deep            # deep | mid | fast (resolves to a model per provider)
  provider: claude      # claude (default) | codex | gemini | ollama
  # pin:                # optional per-provider overrides
  #   ollama: qwen3.6
color: green
tools: Read, Grep, Glob, Bash, Skill
maxTurns: 50
---

<the system prompt — the agent's job, contracts, escalation protocol>
```

- Every agent body enforces four contracts: an **output schema**, an **escalation protocol** (stop and ask, never guess), a **confidence assessment**, and a **turn budget**.
- After any agent change, **run the eval gate**: `dreamteam eval --agent <name> --trials 3`. A spec change isn't done until its scenarios still pass.
- Sync to your harness with `bun scripts/install.ts`; refresh the site labels with `bun scripts/build-site.ts`.

**Checklist:** ☐ frontmatter valid ☐ `bun scripts/install.ts` clean ☐ `dreamteam eval --agent <name> --trials 3` reviewed ☐ `bun scripts/build-site.ts --check` passes.

## Run an agent on another provider

Set `model.provider` in the agent's frontmatter (`codex` | `gemini` | `ollama`) — that's it. Coach K delegates that agent to the provider's first-party CLI on **your subscription** (no proxy, no metered API). Implementation agents (Shaq) go through a plan → approve → implement gate per provider; each provider's write-incapable plan gate is proven by `bun scripts/plan-gate.ts <provider>` before it's enabled. See `docs/spec-hybrid-team/`.

## Before opening a PR

```bash
bun test                       # 0 fail
bun scripts/build-site.ts --check   # site in sync
```

- No agent commits or pushes — and neither should a PR sneak generated `~/.claude/` files in. Only repo source changes.
- Keep counts honest: any "N agents / M scenarios" number on the site is generated by `build-site.ts` from the filesystem — don't hand-edit them.
- Releases publish from CI (push to a branch → `1.0.1-beta.g<sha>` on the `beta` tag; merge to `main` → stable). See `RELEASING.md`.
